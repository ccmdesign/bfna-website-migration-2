# gh#89 — Normaliser: `grid_order` for every project

**Issue:** [#89](https://github.com/ccmdesign/bfna-website-migration-2/issues/89) — promoted residual of #21 (PR #88).
**Epic:** https://app.plane.so/ccm-design/browse/BF-217/
**Spec:** none of its own. The issue body + orchestrator comment are the spec; the defect is
described in the Decisions of `docs/ds-epic/issues/12-composables-projects-programs.md`, and the
code being changed is specified by `docs/ds-epic/issues/07-data-normaliser-core.md`.

## Problem

`scripts/normalise-wireframe-data.ts:313-320` (`gridOrderOf`) emits
`Number.MAX_SAFE_INTEGER` for every project whose program has no entry in `GRID_ORDER`.
Only Democracy (4 slugs) and Future Leadership (3) are placed, so all six grid-eligible
Transatlantic Relations & Global Challenges projects store the same sentinel. A stable sort on
that key is a no-op, and `useBfProjects().gridProjectsByProgram()` therefore renders whatever
order `queryCollection` returns — file-stem, i.e. alphabetical — where `useWfContent` rendered
**snapshot** order.

| | order |
|---|---|
| `useWfContent` (wireframe) | `transatlantic-periscope`, `range`, `transatlantic-barometer`, `astropolitics`, `indo-pacific-nexus`, `critical-minerals` |
| `useBfProjects` (today) | `astropolitics`, `critical-minerals`, `indo-pacific-nexus`, `range`, `transatlantic-barometer`, `transatlantic-periscope` |

Same set, different sequence. It will be visible on the TR&GC program hub (#47/#48).

## Approach

Fix upstream in the normaliser only. Issue 12's spec puts re-deriving curated order out of
scope for the composable ("that logic lives in the normaliser (issue 07) only"), so **the
composable is not touched** — it already just sorts ascending on `grid_order`.

Replace the sentinel with a real ordinal:

```
grid_order = <declared rank>                      when GRID_ORDER places the slug   (0…n-1)
grid_order = 1_000_000 + <index in snapshot items> otherwise
```

Any offset larger than the longest `GRID_ORDER` works; `1_000_000` is comfortably clear of the
38-row snapshot and self-documenting. This keeps placed slugs first in the client's order and
restores snapshot order behind them — which is precisely what `gridSort` did, where unlisted
slugs took `rank = order.length` (a tie that a stable sort resolves to input order) and unlisted
*programs* were returned untouched.

Verified offline against the snapshot: Democracy and Future Leadership have **no** unlisted
grid-eligible members, so the two programs' emitted sequences are unchanged; only TR&GC moves.

   `grid_order` lines.

   sequence equals the wireframe's `gridProjectsByProgram` order, and that Democracy /
   Future Leadership sequences are unchanged. All checks PASS in the generated output.

## Risks

- **Stale comment in the composable.** `useBfProjects.ts:122` documents the
  `Number.MAX_SAFE_INTEGER` sentinel that this change removes. The brief forbids touching the
  composable, so it is left as-is and raised as a residual instead.
- **Offset collision.** None possible: `1_000_000 + 37` is the largest value emitted and every
  declared rank is < 10.
- **Product call.** The issue notes closing as won't-fix was an option (alphabetical is
  arguably fine if the client has no opinion). The orchestrator comment settles it: the
  normaliser must emit `grid_order` for every project so grid order matches the wireframes.
  Recorded, proceeding.
