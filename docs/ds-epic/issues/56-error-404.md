# 56 — error-404 — 404 / error page

One-line objective: rewrite `src/error.vue` to use `bf-default` chrome plus
`bfEmptyState`, distinguishing 404 from 500 while keeping one `h1` and a
back link.

## Context

Depends on #46 (`bf-default`), #33 (`bfEmptyState`). Descends from the "3×
duplicated not-found block" finding (as-built D.1) at the **page** level —
the component-level fix already shipped as `bfEmptyState` in #33; this
issue is the final consumer, closing the finding end to end. Also touches
`src/error.vue`, which is Nuxt's dedicated error-page convention (outside
`pages/`, always rendered on unhandled errors — not itself a route in
epic §7's list but required by it: "404 via `src/error.vue`"). Provenance:
BF-214; D4.

## Scope

- Rewrite `src/error.vue` (existing file, not `pages/wireframes/**`, safe
  to edit):
  - Wrap content in `bf-default` chrome (`<NuxtLayout name="bf-default">`
    — `error.vue` sits outside the pages tree so the layout must be
    invoked explicitly, it is not picked up via `definePageMeta`).
  - Body: `<bf-empty-state :heading="isNotFound ? 'Page not found' : 'Something went wrong'" back-label="Back to home" back-to="/" />`.
  - `isNotFound = computed(() => props.error.statusCode === 404)` drives
    the heading/message split; anything else (500, etc.) gets the generic
    message. One `h1` total (inside `bfEmptyState`, not duplicated by this
    file).
  - Keep the existing `defineProps<{ error: {...} }>()` contract Nuxt's
    error-page convention requires; keep `clearError()`/status-code
    plumbing functionally equivalent to today's file (statusCode drives
    the `<title>` via `useHead`).
- This closes the as-built D.1 finding's third and last consumer — the
  other two (`[area].vue`'s and `insights/[slug].vue`'s inline not-found
  blocks, and `projects/[slug].vue`'s) are replaced by `bfEmptyState`
  directly inside #48/#50/#52's own templates, not here.

## Out of scope

- No edits under `pages/wireframes/**` or `components/wireframe/**` — fails the epic. (The wireframe area keeps its own inline not-found fallbacks unchanged per D2 — this issue does not touch them.)
- Error logging or reporting.
- A custom offline page.

## Styling

- `bfEmptyState` owns its own `--_bf-empty-state-*` variables; this file

## Decisions

### D-56.1 — `404.html` is a client-rendered shell, by framework design

`npx nuxt generate` writes `.output/public/404.html` as an **SPA shell**: an
empty `#__nuxt`, `data-ssr="false"`, no heading, no nav, no footer in the HTML.
That is not a failed prerender and not something this issue can change.
`@nuxt/nitro-server` adds `/200.html` and `/404.html` to the prerender list and
then forces `noSSR` on exactly those paths — `PRERENDER_NO_SSR_ROUTES` in
`node_modules/@nuxt/nitro-server/dist/runtime/utils/renderer/app.mjs`, a
hardcoded `Set`, not a config option — because a static host serves one 404
document for **every** unknown URL and a server-rendered one would bake a single
route's state into all of them.

Consequence for this spec's acceptance: `grep '<h1' .output/public/404.html` is
`0` and always will be. Every assertion about the *rendered* page — one `h1`,
nav and footer around the empty state, axe — is therefore made against the
**hydrated** page in a browser, plus against the SSR render of the same
component under `nuxt dev`, which exercises the identical code path with an
actual server. Both were run; see the issue journal. Adding `/404.html` to
`nitro.prerender.routes` (the github-pages/gitlab-pages preset recipe) does not
help here — those presets add the route, and Nuxt still forces `noSSR` on it.

The static host is what supplies the status code: `npx serve .output/public`
returns **HTTP 404** for `/definitely-not-a-real-page` and for
`/not-a-program`, and Nitro's Netlify preset writes `/* /404.html 404` when
`404.html` exists (`presets/netlify/utils.mjs`), so the deployed behaviour
matches the preview.

### D-56.2 — the back link stays a plain `NuxtLink`, not `clearError({ redirect: '/' })`

The spec asks for the `clearError()` plumbing to stay "functionally equivalent
to today's file". Today's file has **no** `clearError` — it is a bare
`<NuxtLink to="/">` — and that already works, because Nuxt clears the error
itself on any client-side navigation:

```js
// nuxt/dist/pages/runtime/plugins/router.js
if (import.meta.client && !nuxtApp.isHydrating && error.value) await nuxtApp.runWithContext(clearError)
```

So `bfEmptyState`'s `backTo`/`backLabel` pair — the two props this spec names —
is both equivalent and sufficient. Reaching for `clearError({ redirect: '/' })`
would have meant a `@click` handler on slotted content instead of the declared
props, adding a second mechanism for behaviour that already exists. Verified in
the browser against the built output: clicking "Back to home" on the 404 lands
on `/` with the home `h1` and no `.bf-empty-state` left in the document.

### D-56.3 — no probe page, and what stands in for one

`error.vue` is not a route, so a `src/pages/bf-probe/<nn>-*.vue` page cannot
render it in the state under test — a probe would have to instantiate
`bfEmptyState` directly, which is what probe 33 already does. No probe was
added. The substituted checks, all run before the PR opened:

- `npx tsx scripts/check-probes.ts` (full harness) — **38 probes, 1643 rows, 0
  failures**, exit 0, so this change regresses none of the earlier probes.
- `nuxt dev` SSR of a `validate`-rejected route (`/not-a-program`, #182): HTTP
  **404**, exactly one `<h1>` ("Page not found"), 7 `<nav>` and 2 `<footer>`
  elements, and `.bf-empty-state` **inside** `<main id="main">`.
- A throwaway `src/pages/__tmp-500.vue` throwing
  `createError({ statusCode: 500, fatal: true })`, requested with
  `Accept: text/html`: HTTP **500**, one `h1` reading "Something went wrong",
  the generic message, `<title>Error | …</title>`. **Deleted before the first
  commit** — it appears in no commit on this branch.
- axe-core 4.10.2 (`wcag2a, wcag2aa, wcag21a, wcag21aa`) against the hydrated
  404 on the built output: **0 violations**, 22 passes, `color-contrast`
  incomplete (axe's usual "could not determine" on a partially transparent
  ancestor, not a failure).

### D-56.4 — the scoped stylesheet was deleted outright

The file this replaces carried a `<style scoped>` block re-implementing
centring, a measure, vertical rhythm and a pill button, with four `hsl()`
colour literals in it. All four leave the tree and none arrive: `.center` /
`.stack` in `@layer composition` own the box, `bfEmptyState` owns its own
`--_bf-empty-state-padding-block`, and the back link is a plain anchor. The new
`error.vue` declares **no CSS at all** — a small DoD-6 gain rather than a
neutral rewrite.

### D-56.5 — the layout's slot partition takes its fallback branch here

`layouts/bf-default.vue` hoists non-`NuxtPage` slot roots out of `<main>`
(residual #179). Invoked from `error.vue` the slot holds exactly one root, and
it is not a page outlet, so `partitionedSlot()`'s "no page outlet" branch
applies and everything renders **inside** `<main id="main">` — the documented
degrade-to-previous-behaviour path, exercised in production for the first time
by this issue. Asserted directly on the SSR render rather than assumed.
